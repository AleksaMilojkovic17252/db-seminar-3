Result: NO SKEW. Failed at: Session A's COMMIT (step 7 in the runbook's
interleaving table) — both UPDATEs succeeded individually (unlike TiDB's
pessimistic model, CockroachDB never blocks the write itself), but the
conflict is detected as a serialization failure at commit time
(SQLSTATE 40001, RETRY_SERIALIZABLE), and A's entire transaction is
rejected. B's later commit proceeds cleanly since A never actually wrote
its change durably.

Contrast with TiDB/C1: same abstract conflict (two txns each remove one
of the two on-call doctors, both individually valid reads becoming jointly
invalid), but the concurrency-control model determines who catches it and
when. TiDB's default (Snapshot Isolation, pessimistic locking on same-row
writes only) does not catch this at all, since the two writes touch
different rows. CockroachDB's default (Serializable, optimistic validation
against the full transaction's read/write set at commit) catches it
reliably, rejecting whichever transaction's commit loses the race, with
the client responsible for retrying.
