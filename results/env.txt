  actual on-disk footprint observed ~10GB/pod regardless, see Experiment 1's redo notes).
- Service: NodePort, gRPC endpoint at localhost:30010 (distinct from the single-server
  container's port 15026/9010 scheme -- do not confuse the two deployments' ports).

  (2) the chart's default hard pod anti-affinity (requiredDuringScheduling, by hostname)

exp7 bench: crdb run with tidb+spanner stopped; tidb run with crdb+spanner stopped; spanner run with crdb+tidb stopped. Full sweep: 3 workloads x [1,4,16,32,64] threads x 3 reps x 30s.
exp7 bench: REDONE 2026-07-29 against the multi-server deployment (spanner_multi engine, crdb+tidb stopped throughout). Same full sweep. Real, substantial RF=1->RF=3 cost found: point_read barely affected (<15% throughput change at any concurrency); point_write throughput roughly halves at 16+ threads (450->237 ops/sec @ 16 threads) with p99 roughly doubling; transfer hit hardest, throughput drops to ~1/3 (360->101 ops/sec @ 16 threads) and p99 explodes 5x at 64 threads (239ms->1303ms). Counter-intuitively, total retries were LOWER at RF=3 (write workloads attempted far fewer total transactions in the same 30s window). See experiments/07_benchmark/exp7_comparison.md.
exp9 fault tolerance: CockroachDB and TiDB each had 1 node/store killed (kill -9) and manually restarted, 300s window, ~100k combined transactions, 0 failures on either. Spanner Omni originally excluded entirely (RF=1, nothing to kill) -- REDONE 2026-07-29 against the multi-server deployment: leader (spanner-a-1) killed via `kubectl delete pod --grace-period=0 --force`, Kubernetes self-healed automatically in ~61s (no manual restart step exists for this deployment). 32,162 transactions, 0 failures, and unlike CockroachDB/TiDB, no sustained p99 degradation either. See experiments/09_fault_tolerance/exp9_spanner_results.md.
